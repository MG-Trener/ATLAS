# AMR Atlas — черновик методологии surveillance

> Статус: **DRAFT / PROTOTYPE**. Документ задаёт технический контракт для будущих расчётов. До экспертного утверждения не является официальной методикой.

## 1. Единица анализа

Базовая единица хранения — **isolate** с набором связанных AST-результатов.

Минимальный аналитический контекст:

```text
period
region
laboratory
organism
specimen
patient_hash / deduplication key
antimicrobial
AST method
raw result (MIC / zone where available)
interpretation S/I/R
breakpoint standard
breakpoint version/year
```

## 2. Показатель R

Для выбранного среза:

```text
R% = resistant_isolates / interpretable_tested_isolates × 100
```

В знаменатель входят только изоляты с интерпретируемым AST для конкретного препарата после применения правил дедупликации.

На интерфейсе рядом с R должны быть доступны:
- `N tested`;
- `N resistant`;
- период;
- organism;
- antimicrobial;
- specimen filter;
- geography;
- breakpoint standard/version;
- дата обновления;
- provenance/source set.

## 3. Категория I

Atlas не должен автоматически объединять `I` с `R` или `S` без явного методологического правила.

Для EUCAST значение `I` хранится как самостоятельная интерпретационная категория. UI должен показывать S / I / R раздельно там, где это аналитически важно.

## 4. Дедупликация

Правило дедупликации должно быть версионируемым и применяться **до** расчёта агрегатов.

Базовый кандидат для прототипа методологии:
- один isolate organism × patient_hash × аналитический период;
- при повторных изолятах правило выбора задаётся конфигурацией методологии;
- исходные записи не удаляются, агрегат хранит ссылку на версию правила дедупликации.

Перед production необходимо утвердить соответствие национальной методологии и/или WHO GLASS / WHONET-практикам.

## 5. Breakpoints

Нельзя пересчитывать исторический AST без сохранения контекста интерпретации.

Для каждого интерпретированного результата должны быть доступны:
- standard: EUCAST / CLSI / другое;
- версия или год;
- исходный MIC / zone, если передан источником;
- исходная интерпретация источника;
- нормализованная интерпретация Atlas, если выполнялся пересчёт;
- версия алгоритма пересчёта.

Сырые MIC/zone не перезаписываются.

## 6. Малые выборки

Показатель не должен выглядеть статистически равноценным при малом N.

Предварительная UI-политика:
- `N < 10` — показатель не публиковать как процент;
- `10 ≤ N < 30` — показывать с предупреждением `низкая устойчивость оценки`;
- `N ≥ 30` — стандартное отображение;
- пороги должны быть конфигурируемыми и утверждены методологически.

## 7. Доверительные интервалы

Для production-витрины рекомендуется рассчитывать 95% CI для долей R, особенно при региональных сравнениях и ранжировании.

Рейтинг регионов без учёта N/CI не должен трактоваться как статистически доказанное различие.

## 8. MDR / фенотипы / механизмы

MDR, ESBL, CRE, MRSA, VRE и другие показатели должны иметь отдельные версионируемые определения.

Для каждого derived indicator необходимо хранить:
- `definition_code`;
- `definition_version`;
- необходимые organism/agent conditions;
- правила работы с I / missing AST;
- дату вступления правила в действие.

Механизм AMR и фенотипический marker — не одно и то же. Фенотипический сигнал не должен автоматически объявляться подтверждённым генетическим механизмом.

## 9. Качество данных

Каждый агрегат должен сопровождаться как минимум:
- долей обязательных полей;
- долей интерпретируемого AST;
- количеством лабораторий;
- количеством отклонённых записей;
- количеством дублей;
- периодом полноты поступления;
- статусом QC.

## 10. Сигналы

AMR Radar должен разделять:
- статистический/алгоритмический сигнал;
- QC-сигнал;
- подтверждённое аналитиком событие.

Сигнал до верификации нельзя представлять как подтверждённую вспышку или официальное эпидемиологическое событие.

Минимум для карточки сигнала:
- current value;
- baseline;
- delta;
- N;
- период;
- регион;
- организм / препарат / фенотип;
- источник данных;
- алгоритм/правило сигнала;
- статус проверки;
- audit trail.

## 11. Provenance

Любое число на production-экране должно быть воспроизводимо.

Минимальный provenance object:

```json
{
  "dataset_version": "...",
  "updated_at": "...",
  "period_from": "...",
  "period_to": "...",
  "laboratory_count": 0,
  "isolate_count": 0,
  "tested_count": 0,
  "breakpoint_standard": "EUCAST",
  "breakpoint_version": "...",
  "deduplication_rule": "...",
  "indicator_definition": "...",
  "quality_status": "..."
}
```

## 12. Demo provider

Текущий `amr-demo-data.js` используется только для UI/UX-разработки.

Требования:
- значения должны быть детерминированными;
- в интерфейсе постоянно присутствует маркировка `PROTOTYPE / DEMO DATA`;
- demo provider не должен попадать в production-режим после появления валидированного surveillance provider;
- переключение provider должно происходить через data layer, а не переписыванием UI-компонентов.

## 13. Перед первым пилотом необходимо утвердить

1. точное правило дедупликации;
2. единицу отчётного периода;
3. правила S/I/R для разных стандартов;
4. breakpoint version policy;
5. определения MDR/ESBL/CRE/MRSA/VRE;
6. минимальные N для публикации;
7. правила регионального сравнения;
8. QC thresholds;
9. алгоритмы AMR Radar;
10. роли, которые могут подтверждать/отклонять сигнал.
